# Senior QA report: verification and repairs

Reviewed 4–5 November 2026 against the current LedgerPilot backend and browser client. Scope is the approved local P1 pilot. The supplied report contains **37 numbered items**, including positive observations and concerns already addressed by existing controls; its severity totals and some technical explanations are inconsistent. This record uses the individual IDs as the tracking authority.

## Implemented repairs

- **1.2 — MFA enrollment:** assign the locked user query, refresh its identity-map values and refresh the locked factor before checking `verified`. A `FOR UPDATE` query already acquired a database lock even when its result was not assigned; the report's claim that the lock was discarded was incorrect. The additional refresh guards stale ORM state. Missing users fail safely. Already verified factors cannot be overwritten.
- **1.5 — scanner provenance:** version and positive scan verdict now come from one ClamAV `IDSESSION`, with explicit response IDs, bounded terminated replies and fail-closed parsing. A clean verdict is still mandatory. This ties replies to one connection, not an immutable virus-definition snapshot across a server reload. Protocol reference: [official clamd documentation](https://docs.clamav.net/manual/Usage/ClamdProtocol.html).
- **1.6 — rate timing:** `RATE_WINDOW_SECONDS` and `RATE_COOLDOWN_MAX_SECONDS` default to 60, with validated bounds of 1–3600. Authentication, user and business admission all pass the same configured timing. Active cooldowns survive a window rollover or shorter window setting. SQL uses bound parameters; unavailable counters still reject with 503. The message describes request admission rather than incorrectly implying every affected request is a login. Existing budgets and fail-closed behavior remain intact.
- **2.1 — reminders/outstanding balances:** `due_snapshots` aggregates allocations, credits, advances and refund JSON in PostgreSQL, in **one statement for up to two dates**. Reminders calculate historical and current balances together. A later payment must not erase a historical overdue balance; replacing both dates with `date.max`, as the report suggested, would be wrong. Results remain tenant-scoped and exact decimal.
- **2.2 — dashboard:** calculate outstanding balances once and pass the local result to both aging views and control reconciliation. No session/global ORM cache was introduced.
- **2.3, 2.4, 5.2 — report memory:** document, payment/refund, opening-source, account and grouped report inputs read at most 10,001 rows and reject with `ERR_QUOTA`/413 above the 10,000-row pilot bound. They never silently truncate financial totals. Loan controls aggregate in SQL rather than loading every loan. Forecast filters undisputed documents to its next 91 days before reading sources and aggregating their balances.
- **2.5 — checkpoint bounds:** enforce at most 14 distinct balance checkpoints. Retain the existing single grouped query. Arbitrarily switching to lateral joins after six dates has no demonstrated benefit on this workload; production query-plan tuning still needs representative data.
- **2.6 — bank import writes:** explicitly issue a multi-row insert for the bounded imported rows after validating duplicates/conflicts. SQLAlchemy's previous unit of work could already batch inserts, so the report's assertion of 500 round trips was not established. The new form makes batching explicit without bypassing database invariants or tenant scoping.
- **3.1 — registration and SMTP:** persist pending identity/binding changes in the outer transaction and isolate verification issuance/delivery in a savepoint. Catch only `ERR_MAIL_UNAVAILABLE`. Failed delivery rolls back its token/counter changes while preserving the pending account. Failed resend leaves the previously delivered token usable. Restarting signup retires old codes even during an outage. Quota and database failures still propagate and roll back. `flush()` alone would not have fixed the original transaction rollback.
- **3.2, 3.4, 4.1–4.4 — operational logs:** add JSON service/audit, rejection, password-capacity, rate-limit, worker and evidence-export events. Include safe UUID correlation, action, code, error class and bounded stack locations. Never log exception messages, SQL/bindings, passwords, tokens, email addresses, original filenames or storage keys. Unknown audit fields generate an omitted-field count, not their potentially sensitive names or values. `audit.staged` explicitly means transaction pending, not a committed financial outcome. Database audit records remain the durable audit authority. Request logs include verified user/business scope where available; logging context is reset at request completion. Startup re-enables application-owned loggers that an embedded migration may disable.
- **3.5 — invalid invitations:** return `ERR_LINK_EXPIRED`/410 for the stored function's specific invalid/expired invitation error and for an absent result. Unknown database errors retain the existing rollback/safe-handler path. In the current function, invalid invitations raise SQLSTATE 23514, not `NoResultFound`; the report named the wrong cause but exposed an unfriendly response.
- **5.1, 7.2 — bank disposition:** extract journal matching, transfer/card preparation and category-line validation into private helpers. Keep preview and apply on the same validation path and keep mutations, idempotency and canonical journal publishing in one dispatcher. Initialize peer state explicitly and assert it before use.
- **5.3 — operation quota:** replace a full count with a bounded existence probe at offset 9,999. The business row lock still serializes writes; idempotent replays are checked before the quota. This is bounded work, not an O(1) counter. Existing tenant-prefix unique indexes support the lookup; no redundant index or quota-table migration was added.
- **6.1 — mail subjects:** use a fixed purpose-to-friendly-subject allowlist. Reject unknown purposes before SMTP. Never interpolate untrusted subject text.
- **6.2 — actionable authentication:** keep invalid email/password responses generic. Only a correct password reveals pending verification or account unavailability. Signed/owned session failures distinguish access expiry, revoked/expired sessions, changed passwords, account state and inactivity. The browser attempts refresh for access expiry or the legacy generic 401, and immediately routes terminal session failures to sign-in without a refresh loop. Pending-email login opens the existing verification flow; its original-browser CSRF restriction remains enforced.
- **6.3 — resend contract:** document original registration cookie/header binding, generic 202 on an ineligible browser, SMTP savepoint behavior and manual retry in OpenAPI. The browser's message no longer promises an email was definitely sent.
- **6.4 — local mailbox:** `MAILPIT_UI_PORT` defaults to 8025 and configures both the backend's local mailbox link and Compose's host port. SMTP remains a separate port. Defaults require no `.env` edit.
- **7.1 — import maintainability:** preserve `workspace.imports` as a stable public facade and separate schemas, batch compilation and transactional execution under `workspace/importing/`. All four modes share bounded parsing and preloaded account/party inputs. Splitting each row mode into independent database-loading workflows would reintroduce fan-out; the responsibility split retains batch validation and one atomic application transaction.
- **7.3 — settings clarity:** invoke previous-key validation through `type(self)` rather than an instance-bound-looking classmethod call. The same strength check still applies to both keys.

## Verified existing behavior and corrected assumptions

- **1.1:** unsafe requests compare **the exact request header** to both the cookie and session digest, and validate Origin. A stolen access JWT alone does not supply the CSRF proof. Move the redundant missing-family check before validation and document the binding. Existing GET report/snapshot or trial-metadata artifacts are authorized, bounded read support; GET routes do not post financial entries. This does not justify disabling CSRF on command endpoints.
- **1.3:** HS256 remains the accepted modular-monolith signing boundary, with issuer/audience/expiry/rotation checks. A symmetric verifier can sign; do not distribute this key to a future independent verify-only service. Before splitting trust domains, require a dedicated ADR for asymmetric signing, key custody/rotation, verifier rollout and tests. No unapproved identity architecture migration was made.
- **1.4:** HSTS, CSP, Referrer-Policy, Permissions-Policy and related headers already exist in the outer security-header middleware, including CORS/rejections. Hosted HTTPS admission remains enforced. `includeSubDomains` requires control of every affected subdomain and was not blindly enabled.
- **1.7:** secret placeholders are intentionally invalid. No real secret was added to the template or logs.
- **2.7:** the bank-review index already begins with `(business_id, state)`; existing operation unique indexes begin with `business_id`. Adding duplicate indexes would increase write cost. Index presence is regression-checked; large-data planner behavior is not inferred from tiny fixtures.
- **3.3:** unknown database errors already reach a centralized sanitized 409/503 response after rollback; private PostgreSQL messages are not serialized. Keep the narrow known-conflict translations and parameter hiding. Blanket statement-level catches or an incorrect new 500 mapping would weaken this boundary.
- **3.6:** duplicate/conflicting bank sources already roll back the complete import, including a preceding new row. The transaction failure tests retain that guarantee. The error now identifies the offending CSV row position without echoing its source identifier or financial contents; no partial import is accepted.
- **5.4:** keep two nonblocking Argon2 slots. Bounded fail-fast 503 backpressure limits memory/CPU and is intentional, now observable. Automatically retrying hashes or adding an unbounded waiting queue would weaken abuse protection. No client auto-replay of writes was added.
- **6.5:** cursor-list contracts and financial analytical results intentionally differ. Paginating an aging total or adding a fabricated `total` envelope would break semantics and clients. Existing explicit schemas and source quotas remain the contract; new collection endpoints must use the established pagination model.
- **7.4:** export display names were already HTML-escaped and archive links generated from safe identifiers. No injection fix was needed.

## Verification and remaining gates

The real PostgreSQL query-budget checks measure **service calculations**, not a complete browser page or authentication overhead. Dashboard accrual reads dropped from the previously recorded 27 to **13**, and cash reads from 32 to **18**, including the new `WITH` statement in the counter. Both remain constant across the tested two/twelve months and one/five cash accounts. Payment allocation command reads dropped from 31 to **23** and remain constant for one/seven allocations. These are statement counts, not production latency or capacity benchmarks. The 500-row import regression confirms one bank-row insert and zero additional rows on reimport.

The final full run passed **163 backend cases in 823.10 seconds, with zero failures, errors or skips**, using all four service profiles. This includes eight new QA regressions. Also passed **40 component tests, nine transport tests, 11 Chromium regressions**, Ruff lint on source/tests, formatting on source/changed Python tests, mypy on 98 source files, TypeScript/build/format checks, the 126-path OpenAPI contract, generated browser types and 104 requirement references. Traceability references alone are not an acceptance verdict. Test-source fingerprints were checked again after completion; no drift was found.

The initial 32-case backend run and seven then-added QA regressions passed on 4 November. The 5 November first full attempt encountered stopped Docker/local services; an intermediate run was interrupted to include the final cooldown correction. Neither is counted as final evidence. Local services were restored, all eight final targeted cases passed, and the final full run above independently passed. Results, bounds, query counts and source fingerprints are recorded in [the evidence](contracts/qa-findings-results.json).

No schema migration, new provider, broker, paid service, phase-order change, commit, push or deployment is included. Schema remains 0022; Phase 9 deployment is next. Existing Phase 10 manual/deployed checks remain open.

SMTP remains synchronous and bounded by its timeout. This fix provides recoverable pending signup, **not a durable email queue**: users must request resend when mail recovers, and successful SMTP acceptance cannot guarantee inbox delivery or a subsequent database commit. A durable outbox/relay would require separate token encryption/expiry, worker, retry and security design. There is no automatic resend promise.

Reports still use READ COMMITTED and bounded pilot calculations. Constant statement counts do not prove production latency or ten-million-user capacity. Larger histories require measured aggregation/background-report design. Hosted telemetry collection/alerts, deployment security and separate signing trust domains require their deployment gates. The previously recorded moderate development-tool dependency advisory remains open in the security checklist record.
